# API-контракт

**Статус:** рабочий черновик. Открытые бизнес-вопросы перечислены в разделе 11 и требуют согласования.

## 1. Назначение и участники взаимодействия

**Назначение:** API обеспечивает обмен событиями об изменении статуса заказа между внешними системами и маркетплейсом. Полученные события могут приводить к обновлению состояния заказа и отправке PUSH-уведомлений пользователю.

**Участники:**
- **Пользователь** — получатель PUSH-уведомлений.
- **Продавец** — внешняя система, формирующая события в рамках своей ответственности.
- **Служба доставки (СД)** — внешняя система, формирующая события в рамках своей ответственности.
- **Маркетплейс (МП)** — принимающая система, которая проверяет и обрабатывает события, обновляет состояние заказа и определяет необходимость отправки PUSH-уведомления.

## 2. Направление и способ передачи данных

Внешняя система отправляет событие изменения статуса, а маркетплейс принимает и обрабатывает его посредством HTTP-запроса.

Предполагаемый стиль взаимодействия — REST API. Использование HTTPS и требования к авторизации необходимо подтвердить и описать в окончательной версии контракта.

## 3. Endpoint и HTTP-метод

**Метод:** `POST`

**Шаблон endpoint:** `https://marketplace.api.ru/orders/{orderId}/events/`

`{orderId}` — идентификатор заказа в пути запроса. Вопрос о необходимости дублировать `orderId` в теле запроса оставлен открытым в разделе 11.

## 4. Структура запроса

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `eventId` | String | Да | Идентификатор события. Правило уникальности требуется уточнить. |
| `orderId` | String | Требует согласования | Идентификатор заказа. Решить, передаётся ли он также в теле запроса, если уже присутствует в URL. |
| `itemId` | String | Нет, по текущему предположению | Идентификатор конкретного товара. Уточнить, допускаются ли события, относящиеся ко всему заказу. |
| `timestamp` | String (ISO 8601) | Да | Время возникновения события в UTC. Пример: `2026-10-09T12:30:00Z`. |
| `status` | String | Да | Машинный код нового статуса из справочника в разделе 10. |

## 5. Пример запроса

Пример ниже показывает событие, относящееся к конкретному товару. Наличие `orderId` в теле зависит от решения, указанного в разделе 11.

```http
POST https://marketplace.api.ru/orders/ord_111/events/
Content-Type: application/json
```

```json
{
  "eventId": "event-111",
  "itemId": "it_1477",
  "timestamp": "2026-10-09T12:30:00Z",
  "status": "IN_TRANSIT"
}
```

## 6. Успешный ответ

**Предварительный вариант:** `200 OK` — событие принято и успешно обработано.

Это значение предполагает синхронную обработку. Если событие только помещается в очередь и будет обработано позже, код ответа и описание поведения необходимо пересмотреть.

## 7. Ошибки и их обработка

### Пример сценария

В URL указан заказ `ord_123`, а в теле запроса — `ord_128`. Такой запрос демонстрирует несоответствие идентификаторов, если `orderId` оставляется в обоих местах.

Окончательный код ответа зависит от согласованного правила:
- `404 Not Found` — если заказ, указанный в пути, не найден;
- ошибка валидации — если оба идентификатора присутствуют, но не совпадают.

Необходимо различать отсутствие заказа и несоответствие идентификаторов.

## 8. Повторные запросы и идемпотентность

Повторная доставка уже обработанного события не должна приводить к повторному изменению состояния или повторной отправке PUSH.

### Пример повторного запроса

```http
POST https://marketplace.api.ru/orders/ord_123/events/
Content-Type: application/json
```

```json
{
  "eventId": "event-0123",
  "itemId": "it_98",
  "timestamp": "2026-10-09T12:30:00Z",
  "status": "IN_TRANSIT"
}
```

**Критерий дубликата и ответ на повторный запрос требуют согласования.** В частности, необходимо определить, достаточно ли совпадения `eventId` или требуется дополнительная проверка содержимого события.

## 9. Тайм-ауты и политика повторных попыток

- **Количество повторных попыток:** 3.
- **Тайм-аут ожидания ответа:** требуется определить.
- **Интервал между попытками:** требуется определить.
- **Повторяемые ошибки:** требуется определить, какие ошибки допускают повторный запрос.
- **После исчерпания попыток:** отправляющая система сохраняет событие как необработанное, помечает его важность/срочность и активирует Alert. Ответственность за последующую обработку и механизм повторного запуска необходимо уточнить.

Следует отдельно определить поведение на случай, когда принимающая система обработала событие, но отправитель не получил ответ и повторил запрос.

## 10. Статус-коды

| Код | Пользовательская формулировка |
|---|---|
| `PROCESSING` | Заказ оформляется |
| `TRANSFERRED_TO_SELLER` | Заказ передан продавцу |
| `ASSEMBLING` | Заказ собирается |
| `IN_TRANSFER_TO_DS` | Заказ передается в службу доставки |
| `TRANSFERRED_TO_DS` | Заказ передан в службу доставки |
| `IN_TRANSIT` | Заказ в пути |
| `PARTIALLY_DELAYED` | Заказ частично задерживается |
| `DELAYED` | Заказ задерживается |
| `PARTIALLY_DELIVERED` | Заказ частично доставлен |
| `DELIVERED` | Заказ доставлен |
| `RECEIVED` | Заказ получен |
| `CANCELED` | Заказ отменен |
| `RETURNED` | Возврат |

Справочник приведён по текущему черновику. Необходимо проверить, какие коды применяются к состоянию товара, какие — к агрегированному состоянию заказа, и соответствуют ли названия кодов смыслу бизнес-статусов.

## 11. Допущения и открытые вопросы

1. Должен ли `orderId` передаваться одновременно в URL и теле запроса?
2. Может ли событие изменения статуса относиться ко всему заказу без `itemId`?
3. Как определяется дубликат: по `eventId` или по совокупности полей события?
4. Какие ошибки допускают повторный запрос и каков интервал между попытками?
5. Что делать с накопленными уведомлениями после восстановления сервиса: отправлять все, только актуальные или объединять?
6. Какой код ответа возвращается при повторном событии и при принятии события в очередь?
7. Как различаются ошибка «заказ не найден» и ошибка несовпадения идентификаторов?
8. Какой механизм авторизации используется для внешних систем?
